# OPIc 코치를 위한 STT 도메인 안내서

## 1. STT는 무엇인가

STT는 Speech-to-Text의 줄임말이다. 사람이 낸 소리를 컴퓨터가 글자로 옮기는
기술이다.

아주 쉽게 말하면 받아쓰기 선생님이다.

```text
귀로 들은 소리 → 어떤 말인지 추측 → 글자로 적기
```

하지만 OPIc 코치의 받아쓰기 선생님은 일반 회의록 서비스와 목표가 다르다.

- 회의록은 읽기 좋은 문장이 중요하다.
- OPIc 코치는 사용자가 실제로 어떻게 말했는지가 중요하다.

따라서 `I, I went... um... there yesterday`를 자연스럽게 고쳐
`I went there yesterday.`라고 만들면 읽기는 좋지만 학습 데이터로는 나쁘다.
반복과 필러가 사라져 유창성 문제를 볼 수 없기 때문이다.

## 2. OPIc 전사의 품질 정의

이 프로젝트에서 좋은 전사는 다음을 만족해야 한다.

1. 말한 단어를 빠뜨리지 않는다.
2. 말하지 않은 단어를 만들지 않는다.
3. `um`, `uh`, `er`, `hmm` 같은 필러를 보존한다.
4. 반복과 말 더듬기를 보존한다.
5. 끝내지 못한 문장을 마음대로 완성하지 않는다.
6. 틀린 문법, 시제, 어휘를 교정하지 않는다.
7. 고유명사와 OPIc 주제 단어를 가능한 정확히 적는다.
8. 신뢰가 낮은 부분을 숨기지 않고 사용자 확인 대상으로 표시한다.

즉, 목표는 “예쁜 글”이 아니라 “충실한 기록”이다.

## 3. STT 파이프라인의 여덟 층

```text
사람의 발화
  ↓
① 마이크와 환경
  ↓
② 디지털 오디오
  ↓
③ container와 codec
  ↓
④ 음성 구간 탐지
  ↓
⑤ 음성 인식 모델
  ↓
⑥ decoding과 문맥 힌트
  ↓
⑦ 후처리와 신뢰도
  ↓
⑧ 사용자 검토
```

전사 오류가 발생했다고 항상 모델만 바꿔서는 안 된다. 마이크 입력이 깨졌거나,
codec이 맞지 않거나, 음성 구간이 잘린 문제일 수도 있다.

## 4. 마이크와 녹음 환경

모델이 아무리 좋아도 입력에 없는 소리는 복원할 수 없다.

품질에 영향을 주는 대표 요인:

- 마이크와 입의 거리
- 마이크 gain
- 방의 울림
- 선풍기, 키보드, 음악 같은 배경 소음
- Bluetooth 연결 품질
- 여러 입력 장치가 동시에 존재하는 환경
- 브라우저의 자동 gain, echo cancellation, noise suppression

초기 개선에서는 “최고의 모델”보다 사용자가 실제 목소리가 녹음되는지 확인할 수
있는 재생 UI와 입력 안내가 더 큰 효과를 낼 수 있다.

## 5. 디지털 오디오의 기초

### Sample rate

1초의 소리를 몇 번 측정했는지 나타낸다. 예를 들어 16kHz는 1초에 16,000개의
sample을 가진다. 브라우저 MediaRecorder에서는 실제 sample rate를 브라우저와
codec이 결정할 수 있다.

### Channel

모노는 한 줄, 스테레오는 두 줄의 소리를 가진다. 현재 프론트엔드 로컬 분석은 첫
번째 채널만 읽는다.

### Bitrate

1초 오디오를 저장하는 데 사용하는 bit 수다. 현재 녹음 요청 값은 48kbps다.
낮으면 파일은 작아지지만 압축 손실이 커질 수 있다.

### Container와 codec

- container는 소리를 담는 상자다: WebM, MP4, WAV
- codec은 상자 안에서 소리를 압축하는 방법이다: Opus, AAC, PCM

파일 확장자가 같아도 codec이 다를 수 있다. header 검사만으로 전체 오디오를 정상
decode할 수 있는지 확정할 수 없다.

## 6. VAD와 청킹

VAD는 Voice Activity Detection의 줄임말로, “여기는 말하는 부분이고 여기는
침묵”이라고 구간을 나누는 기술이다.

청킹은 긴 오디오를 작은 조각으로 자르는 일이다.

좋은 점:

- 긴 입력을 안정적으로 처리할 수 있다.
- 긴 침묵을 제외할 수 있다.
- 일부 실패 구간만 다시 처리할 수 있다.

위험:

- 단어 앞이나 뒤가 잘릴 수 있다.
- 긴 생각 시간이 답변에서 사라질 수 있다.
- 조각 경계에서 문맥을 잃을 수 있다.
- OPIc 유창성 평가에 필요한 pause가 왜곡될 수 있다.

OpenAI 전사 API는 단일 블록 처리 외에 자동 VAD 기반 chunking 옵션을 제공한다.
하지만 최대 2분인 현재 답변에서는 무조건 켜기보다 긴 침묵과 느린 발화 fixture로
비교해야 한다.

공식 참고:
[Create transcription](https://developers.openai.com/api/reference/cli/resources/audio/subresources/transcriptions/methods/create)

## 7. 음성 인식 모델

음성 인식 모델은 오디오 특징을 보고 어떤 글자와 단어일 가능성이 높은지 계산한다.
모델 선택에서 볼 항목은 다음과 같다.

- 비원어민 영어 정확도
- 한국인 영어 억양에 대한 정확도
- 필러와 반복 보존
- 고유명사와 주제 어휘
- 긴 침묵과 다시 시작한 문장 처리
- latency
- 비용
- rate limit
- 버전 고정 가능 여부

현재 기본 모델은 `gpt-4o-mini-transcribe`다. OpenAI 공식 문서는 모델 별칭과 고정
snapshot을 함께 제공한다. 별칭은 나중에 동작이 갱신될 수 있고 snapshot은 같은
버전을 재현하는 데 유리하다.

공식 참고:
[GPT-4o Mini Transcribe](https://developers.openai.com/api/docs/models/gpt-4o-mini-transcribe)

## 8. 언어와 문맥 힌트

입력 언어를 알려주면 모델이 후보 범위를 줄일 수 있다. OpenAI 공식 API 문서도
ISO-639-1 언어를 제공하면 정확도와 latency 개선에 도움이 된다고 설명한다. 현재
프로젝트는 OPIc 영어 답변이므로 `en`을 보낸다.

prompt 또는 keyword는 고유명사와 주제 어휘 인식을 도울 수 있다. 하지만 다음 위험이
있다.

- 질문에 나온 단어를 사용자가 말하지 않았는데 추가할 수 있음
- 사용자의 잘못된 단어를 의도한 단어로 교정할 수 있음
- 문장을 자연스럽게 다듬을 수 있음

따라서 질문 전체를 무조건 주지 않는다. 다음 실험을 분리해 비교한다.

1. 문맥 없음
2. 전사 스타일 지시만 제공
3. 주제별 허용 어휘 목록만 제공
4. 질문 문장까지 제공

OPIc 코치에서는 단순 WER뿐 아니라 환각 단어와 오류 보존율을 함께 측정해야 한다.

## 9. 전사 정규화와 후처리

일반 STT 서비스는 다음을 자동으로 할 수 있다.

- 대문자와 문장부호 추가
- 숫자 표기 통일
- 필러 제거
- 반복 제거
- 문법 교정처럼 보이는 매끄러운 변환

OPIc 평가에서는 원본 보존용 전사와 읽기 편한 표시용 전사를 분리해야 한다.

추천 데이터 구조:

```text
rawTranscript       모델이 반환한 원문
displayTranscript   화면 표시를 위한 최소 정규화 결과
editedTranscript    사용자가 확인한 최종 문장
```

현재 구현은 `rawText`와 `editedText`만 사용한다. 표시용 정규화 계층이 정말 필요한지는
사용자 테스트 후 결정한다.

## 10. 신뢰도와 log probability

모델은 각 token 후보가 얼마나 가능하다고 생각했는지 log probability로 표현할 수
있다. 값이 낮다고 반드시 틀린 것은 아니지만, 사용자가 확인할 위치를 고르는 데
도움이 된다.

OpenAI 공식 API에서 일부 전사 모델은 JSON 응답과 함께 `logprobs`를 포함할 수 있다.

신뢰도 사용 원칙:

- 정답 또는 오답으로 단정하지 않는다.
- 연속된 낮은 확신 token을 사람이 읽을 수 있는 구간으로 묶는다.
- threshold는 실제 평가 자료로 조정한다.
- 낮은 확신 구간이 많아도 원문 전체를 버리지 않는다.
- UI에는 “다시 확인해 주세요”로 표현한다.

공식 참고:
[Create transcription](https://developers.openai.com/api/reference/cli/resources/audio/subresources/transcriptions/methods/create)

## 11. Timestamp

단어 또는 문장 구간의 시작·끝 시간을 알면 다음 기능을 만들 수 있다.

- 낮은 신뢰 단어를 눌러 해당 오디오 재생
- 긴 pause 위치 확인
- 발화 속도의 시간대별 변화
- 전사문과 파형 동기화

하지만 timestamp는 모델과 응답 형식에 따라 지원 범위가 다르다. 현재 기본 전사
응답은 전체 text만 사용한다. timestamp가 꼭 필요한 제품 기능인지 먼저 결정한 뒤
모델과 API 형식을 선택해야 한다.

## 12. STT가 할 수 없는 평가

텍스트 전사만으로 다음을 정확히 판단할 수 없다.

- `r`과 `l` 같은 개별 음가
- 단어 강세
- 문장 억양
- 목소리의 명료도
- 마이크 음질
- STT가 아예 빠뜨린 필러

발음을 평가하려면 timestamp가 있는 음성 분석, phoneme alignment, acoustic model 같은
별도 계층이 필요하다. 전사문만 읽는 평가 LLM이 발음 피드백을 생성하면 근거 없는
추측이 된다.

## 13. RAG와 파인튜닝의 위치

### RAG

RAG는 필요한 문서를 찾아 LLM에 제공하는 기술이다. 평가 LLM에 OPIc rubric,
질문 유형별 전략, 승인된 예시 답변을 제공하는 데 유용하다.

RAG가 마이크 소리를 더 잘 듣게 만들지는 않는다. STT의 주제 어휘 힌트로 제한적으로
사용할 수 있지만, 말하지 않은 단어를 추가하는 편향을 반드시 측정해야 한다.

### 파인튜닝

검수된 입력과 정답 쌍을 많이 모아 모델의 일관된 행동을 학습시키는 방법이다.
다음 조건이 먼저 필요하다.

- 무엇을 개선할지 명확한 평가 지표
- 개인정보 사용 동의와 보존 정책
- 사람이 검수한 충분한 정답 자료
- train, validation, test 분리
- 기존 prompt 또는 RAG보다 실제로 나은지 비교

처음부터 파인튜닝하면 데이터 오류까지 학습할 수 있다. 현재 순서는
`평가 자료 → baseline → prompt와 모델 비교 → 필요 시 RAG/파인튜닝`이다.

## 14. OPIc STT 설계 원칙

1. 자연스러움보다 원문 충실도를 우선한다.
2. STT 오류와 평가 LLM 오류를 별도로 측정한다.
3. 음향 지표와 텍스트 지표를 섞어 과장하지 않는다.
4. 사용자가 수정할 수 있는 human-in-the-loop를 유지한다.
5. 모델과 prompt 변경 전후를 같은 평가 자료로 비교한다.
6. 운영 음성과 전사문을 기본 로그에 남기지 않는다.
7. 별칭과 snapshot의 재현성 차이를 기록한다.
8. latency, 비용, 품질을 함께 최적화한다.
