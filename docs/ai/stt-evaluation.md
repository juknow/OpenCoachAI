# STT 품질 평가 방법

## 1. 왜 시험지가 먼저 필요한가

STT 모델이나 prompt를 바꾼 뒤 전사문 몇 개를 눈으로 보는 것만으로는 개선 여부를
알 수 없다. 쉬운 음성만 좋아지고 작은 목소리나 필러가 많은 음성은 나빠질 수 있다.

따라서 모델을 바꾸기 전에 항상 같은 문제를 풀게 하는 “STT 시험지”를 만든다.

```text
고정 음성 + 사람이 검수한 정답 전사문
                  ↓
기존 설정과 새 설정이 같은 시험을 봄
                  ↓
정확도·필러·환각·시간·비용을 함께 비교
```

## 2. 평가 단위

한 평가 sample은 다음 정보를 가진다.

```json
{
  "id": "clean-filler-001",
  "audioPath": "samples/clean-filler-001.webm",
  "referenceTranscript": "Um, I I usually go there on weekends.",
  "tags": ["clean", "filler", "repetition"],
  "durationSeconds": 5.8,
  "language": "en",
  "consent": "synthetic-or-explicit-test-consent"
}
```

`referenceTranscript`는 두 명 이상이 들었을 때 같은 내용으로 합의할 수 있는 사람이
검수한 정답이다. 들리지 않는 부분을 억지로 추측하지 않고 별도 표기 규칙을 정한다.

## 3. 평가 자료 구성

초기 자료는 최소한 다음 범주를 골고루 포함한다.

| 범주 | 확인하려는 문제 |
|---|---|
| 깨끗한 보통 속도 | 기본 정확도 |
| 작은 목소리 | 낮은 신호에서의 누락 |
| 일정한 배경 소음 | 소음을 단어로 만드는지 |
| 빠른 발화 | 단어 합침과 누락 |
| 느린 발화 | 과도한 문장 분리와 기다림 |
| 긴 첫 침묵 | 시작 부분 손실과 latency |
| 긴 중간 pause | VAD와 chunk 경계 |
| 필러 다수 | `um`, `uh` 보존 |
| 연속 반복 | `I I`, `the the` 보존 |
| false start | 다시 시작한 문장 보존 |
| 틀린 문법 | 자동 교정 여부 |
| 틀린 어휘 | 의도 추측과 교체 여부 |
| 한국식 고유명사 | 이름과 장소 인식 |
| OPIc 주제 어휘 | 집, 공원, 여행, 역할극 어휘 |
| 아주 짧은 답변 | 3초 안팎 입력 |
| 긴 답변 | 120초에 가까운 입력 |
| 무음 | 빈 결과와 오류 처리 |
| 비음성 잡음 | 환각 문장 생성 여부 |
| 손상된 파일 | 안전한 입력 오류 처리 |

한 사람의 목소리만 사용하면 그 사람에게 과하게 맞춘 결과가 된다. 가능하면 성별,
음높이, 말하기 속도, 영어 숙련도가 다른 화자를 포함한다.

## 4. 개인정보와 fixture 정책

- 운영 사용자의 녹음을 자동으로 평가 자료에 넣지 않는다.
- 합성 음성은 pipeline 테스트에는 사용할 수 있지만 비원어민 발화 품질 평가를 대신할
  수 없다.
- 실제 화자 자료는 명시적 동의, 사용 목적, 보존 기간, 삭제 방법을 기록한다.
- 이름, 학교, 회사, 주소 등 개인 식별 정보가 포함된 sample은 사용하지 않는다.
- 공개 저장소에 넣을 수 없는 오디오는 별도 접근 제어 저장소에 두고 manifest만 관리한다.
- Git에 큰 binary를 직접 계속 추가하지 않는다. 필요하면 Git LFS 또는 전용 저장소를
  선택하고 ADR로 기록한다.

## 5. 텍스트 정규화 규칙

WER 계산 전 비교에 불필요한 표기 차이를 정규화한다.

권장 기본 정규화:

1. 소문자로 변환
2. 평가 대상이 아닌 문장부호 제거
3. 연속 공백을 하나로 변환
4. apostrophe 표기를 통일

정규화하면 안 되는 것:

- 필러 제거
- 반복 단어 제거
- 문법 교정
- 숫자와 단어 표기를 근거 없이 같은 것으로 간주
- false start 삭제

원문 보존 품질을 측정해야 하므로 평가 목표인 차이를 지워서는 안 된다.

## 6. 핵심 품질 지표

### 6.1 Word Error Rate

```text
WER = (대체한 단어 + 빠뜨린 단어 + 추가한 단어) / 정답 단어 수
```

낮을수록 좋다. 전체 정확도를 한 숫자로 비교하기 좋지만 OPIc에 중요한 필러와
문법 오류 보존 여부를 따로 설명하지 못한다.

### 6.2 삭제율

정답에 있었지만 STT가 빠뜨린 단어 비율이다. 작은 목소리, 빠른 발화, 문장 끝이 자주
누락되는지 확인한다.

### 6.3 삽입률과 환각률

사용자가 말하지 않았는데 STT가 추가한 단어의 비율이다. 무음·잡음에서 완성된
문장을 만들면 치명적인 실패로 별도 집계한다.

### 6.4 필러 보존율

```text
올바르게 보존한 필러 수 / 정답 필러 수
```

필러가 없는 sample은 이 지표의 분모에서 제외한다. 필러의 위치까지 맞았는지도
검토할 수 있다.

### 6.5 반복 보존율

정답에 있는 연속 반복과 false start가 전사문에 남았는지 측정한다. 일반 WER가 같아도
반복을 지운 모델은 OPIc 유창성 분석에 불리하다.

### 6.6 오류 보존율

사람이 실제로 말한 문법·시제·어휘 오류를 STT가 자연스럽게 교정하지 않고 그대로
남겼는지 측정한다.

### 6.7 핵심 어휘 정확도

장소명, 사람 이름, OPIc 주제 핵심어처럼 의미에 큰 영향을 주는 단어를 별도 목록으로
표시해 recall을 계산한다.

### 6.8 빈 전사율

실제 음성이 있는 sample에서 빈 문자열 또는 공백만 반환한 비율이다.

### 6.9 비음성 환각률

무음이나 비음성 잡음 sample에서 실제 단어나 문장을 생성한 비율이다. 가능하면 0이어야
한다.

## 7. 운영 지표

품질만 좋고 너무 느리거나 비싸면 제품에서 사용할 수 없다.

| 지표 | 의미 |
|---|---|
| latency p50 | 보통 사용자가 기다리는 시간 |
| latency p95 | 느린 요청이 기다리는 시간 |
| 성공률 | 정상 응답 비율 |
| timeout 비율 | 제한 시간을 넘긴 요청 비율 |
| retry 비율 | rate limit 등으로 다시 호출한 비율 |
| 오디오 1분당 비용 | 모델 비교를 위한 비용 기준 |
| 입력 1분당 token/usage | 비용 변화 원인 분석 |
| 형식별 실패율 | WebM, MP4 등 호환성 확인 |

운영 로그에는 sample ID 같은 비민감 식별자만 사용하고 오디오 또는 전사 내용을
기본 로그에 포함하지 않는다.

## 8. 실험 단위

하나의 실험에서는 가능한 한 한 변수만 바꾼다.

좋은 실험:

- 같은 모델에서 prompt A와 B 비교
- 같은 prompt에서 mini 모델과 상위 모델 비교
- 같은 설정에서 alias와 고정 snapshot 비교
- 같은 모델에서 chunking 없음과 자동 VAD 비교

나쁜 실험:

- 모델, prompt, bitrate, VAD를 한꺼번에 변경

여러 변수를 동시에 바꾸면 어떤 변경이 결과를 만들었는지 알 수 없다.

## 9. 실험 기록 형식

각 실행은 다음 정보를 남긴다.

```json
{
  "experimentId": "2026-09-mini-prompt-b",
  "model": "모델 또는 snapshot ID",
  "promptVersion": "transcription-v2",
  "audioConfig": {
    "chunking": "none",
    "language": "en"
  },
  "datasetVersion": "stt-eval-v1",
  "metrics": {
    "wer": 0.0,
    "fillerRecall": 0.0,
    "repetitionRecall": 0.0,
    "hallucinationRate": 0.0,
    "latencyP50Ms": 0,
    "latencyP95Ms": 0,
    "estimatedCostPerAudioMinute": 0.0
  }
}
```

실제 전사문은 민감 정보가 없는 승인된 평가 자료에 대해서만 별도 결과 파일에 저장한다.

## 10. 채택 판단

새 설정은 평균 WER 하나만 좋아졌다고 채택하지 않는다.

필수 gate:

- 비음성 환각률이 악화되지 않음
- 필러 보존율이 악화되지 않음
- 반복과 오류 보존율이 악화되지 않음
- 중요한 화자·환경 범주에서 치명적인 regression이 없음
- latency와 비용이 제품 허용 범위 안에 있음
- 동일 설정으로 반복 실행했을 때 결과가 허용 범위 안에서 재현됨

초기 수치 목표는 baseline을 측정한 뒤 정한다. 근거 없이 임의 목표를 먼저 정하지 않는다.

## 11. 평가 자료 분리

자료가 충분해지면 다음 세 묶음으로 나눈다.

- **development set**: prompt와 설정을 조정할 때 사용
- **validation set**: 후보 설정을 비교할 때 사용
- **test set**: 최종 선택 전에만 사용

같은 화자의 비슷한 문장이 여러 묶음에 들어가면 실제보다 성능이 좋아 보일 수 있다.
가능하면 화자 단위로 분리한다.

## 12. 첫 번째 평가 도구 구현 순서

1. 민감 정보가 없는 sample manifest schema를 정의한다.
2. 정답 전사문 정규화 규칙에 단위 테스트를 추가한다.
3. 단어 정렬과 WER 계산기를 구현한다.
4. 필러와 반복 보존 지표를 구현한다.
5. 무음·비음성 결과 판정을 구현한다.
6. provider 설정별 실행 adapter를 구현한다.
7. latency와 usage를 수집한다.
8. JSON 결과와 사람이 읽는 Markdown 요약을 생성한다.
9. CI에서는 비용 없는 고정 결과 fixture로 계산기만 테스트한다.
10. 실제 외부 API 평가는 명시적으로 실행하는 별도 명령으로 둔다.

## 13. 완료 조건

- 같은 dataset과 설정으로 결과를 다시 만들 수 있다.
- metric 계산이 자동 테스트로 검증된다.
- 모델과 prompt 변경 PR에 이전/이후 비교표가 포함된다.
- 음성과 전사문이 일반 애플리케이션 로그에 노출되지 않는다.
- 품질, latency, 비용 중 어느 하나를 숨기고 “개선”이라고 표현하지 않는다.

## 14. 현재 구현 상태

현재 저장소에는 다음 오프라인 평가 기반이 구현되어 있다.

- `backend/app/evals/transcription_dataset.py`: 평가 manifest 계약
- `backend/app/evals/transcription_run.py`: 모델 실행 결과 계약
- `backend/app/evals/transcription_metrics.py`: WER, 필러, 연속 반복어 지표
- `backend/app/evals/transcription_report.py`: 전체 및 sample별 성적표 계산
- `backend/app/evals/transcription_cli.py`: JSON 성적표 생성 CLI
- `backend/app/evals/transcription_execute_cli.py`: 동의 평가 음성의 로컬 Whisper 실행 및 run JSON 생성 CLI
- `backend/evals/transcription/`: 공개 예시와 로컬 자료 배치 안내

아직 구현하지 않은 항목:

- 동의받은 실제 비원어민 평가 음성 세트
- OpenAI 등 다른 STT 공급자의 실제 실행 adapter와 설정 비교 게이트
- false start와 사람이 표시한 문법·어휘 오류의 보존 지표
- 실제 API usage를 이용한 오디오 1분당 비용 집계
- 두 실험 결과를 gate 기준으로 자동 비교하는 명령

현재 CLI는 이미 저장한 모델 실행 결과를 평가하며 외부 API를 호출하거나 비용을
발생시키지 않는다. 실행 방법은
`backend/evals/transcription/README.md`에 기록되어 있다.
