# ADR 0002: STT 평가기를 독립 실행하고 native 결과를 보존한다

- 상태: 승인된 구현
- 날짜: 2026-09-25

## 문제

기존 자체 평가는 하나의 안정된 기준을 제공하지만 외부 표준 도구와 verbatim 전용 도구를
같은 Gold·Prediction으로 반복 검증하기 어렵다. 반대로 모든 결과를 공통 점수로 바꾸면
평가기마다 다른 정규화와 입력 의미가 가려진다.

## 결정

공통 Evaluator 계약과 명시적 registry를 두고, 오케스트레이터가 선택된 평가기를 제한된
동시성으로 독립 실행한다. 각 평가기의 native 결과는 별도 파일에 저장하고 최소 실행
인덱스만 만든다. 기존 Custom 평가기는 기존 엔진을 호출해 의미를 유지한다.

Nyra는 pip 패키지로 가장하지 않고 공식 source checkout을 subprocess bridge로 호출한다.
SCTK는 실제 `sclite` 바이너리만 호출한다. 설치 또는 입력이 부족하면 가짜 결과 대신
`unsupported`를 기록한다.

## 선택 이유

- 평가기 하나의 장애가 다른 평가 결과를 없애지 않는다.
- 저장된 답안을 재사용하므로 새 평가기를 붙여도 STT 모델을 재호출하지 않는다.
- raw 결과가 남아 upstream 버전과 해석이 바뀌어도 원래 결과를 다시 확인할 수 있다.
- 명시적 등록은 임의 plugin 탐색보다 설치 상태와 실행 범위를 검토하기 쉽다.
- 로컬 불변 파일은 현재 연구 규모에 충분하며 새 DB·API·queue의 운영 비용을 만들지 않는다.

## 검토했지만 선택하지 않은 대안

### 모든 평가기를 제품 Docker 이미지에 포함

한 명령으로 실행하기는 쉽지만 SCTK 빌드, Nyra checkout, MeetEval의 플랫폼별 빌드 문제를
FastAPI·Whisper 제품 이미지에 전파한다. 평가 도구 변경이 제품 배포를 막을 수도 있어
선택하지 않았다.

### 공통 점수 스키마와 자동 비교 보고서

보기는 쉽지만 서로 다른 정규화와 목적을 가진 WER을 같은 값처럼 오해하게 한다. 사용자
요구 범위에서도 비교·종합·순위는 제외되었으므로 구현하지 않았다.

### 새로운 PostgreSQL/API/worker

여러 서버가 같은 작업을 배분해야 할 때는 유용하다. 현재 요구는 저장된 로컬 JSON과
원본 결과의 반복 평가이며 기존 파일 구조로 충족되므로 도입하지 않았다.

## 영향

- 평가 전용 Python 의존성은 `requirements-benchmark.txt`로 분리된다.
- 외부 실행 파일과 source checkout은 사용자가 명시적으로 제공한다.
- 동일 평가 실행 ID는 덮어쓰지 않는다.
- 비교와 채택 판단은 사람이 native 결과와 입력 계약을 확인해 수행한다.

## 재검토 조건

- 여러 서버가 동시에 같은 연구 저장소를 갱신해야 한다.
- 감사 요구로 중앙 권한·보존·삭제 이력이 필요하다.
- Linux에서 SCTK·Nyra·MeetEval을 고정 버전으로 반복 실행할 전용 이미지가 필요하다.
