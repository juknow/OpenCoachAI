# Git 브랜치와 커밋 규칙

## 아주 쉽게 설명하면

Git 작업은 그림을 그리는 것과 비슷하다.

- `main`은 전시회에 걸어도 되는 완성 그림이다.
- `develop`은 다음 전시회를 준비하는 공동 작업판이다.
- 작업 브랜치는 한 가지 부분만 고치는 개인 스케치북이다.
- 커밋은 스케치북에 남기는 작은 저장 지점이다.
- Pull Request는 작업한 이유와 결과를 함께 확인하는 검토 요청이다.

## 브랜치 역할

| 브랜치 | 역할 | 직접 작업 |
|---|---|---|
| `main` | 배포 가능한 안정 버전 | 금지 |
| `develop` | 다음 배포의 통합 버전 | 금지 |
| `codex/feat-*` | 새로운 기능 | 허용 |
| `codex/fix-*` | 버그 수정 | 허용 |
| `codex/refactor-*` | 동작을 유지하는 구조 개선 | 허용 |
| `codex/docs-*` | 문서 작업 | 허용 |
| `codex/test-*` | 테스트와 평가 도구 | 허용 |

사람이 직접 만드는 브랜치는 `feat/`, `fix/`, `refactor/`, `docs/`, `test/`를
사용할 수 있다. 에이전트가 만드는 브랜치는 누가 만들었는지 바로 알 수 있도록
`codex/` 접두사를 붙인다.

## 현재 저장소의 예외 상태

현재 OPIc Coach 구현은 `variant/opicoach`에 있고 `main`과 `develop`에는 아직 없다.
따라서 이 구현을 다루는 초기 작업은 `variant/opicoach`에서 분기한다.

```text
main / develop
       
        └── variant/opicoach
                 └── codex/docs-transcription-foundation
```

전사 기반 작업이 검증되어 `develop`에 통합된 이후에는 모든 새 작업을
`develop`에서 시작한다. 기준 브랜치를 바꾸는 작업은 별도 Pull Request로 처리한다.

## 작업 흐름

1. 작업 전에 기준 브랜치를 최신 상태로 확인한다.
2. 하나의 목적을 가진 작업 브랜치를 만든다.
3. 현재 동작을 코드와 테스트로 확인한다.
4. 가장 작은 논리 단위로 구현하고 테스트한다.
5. 상세한 한글 제목과 본문으로 커밋한다.
6. 커밋별로 관련 없는 변경이 섞이지 않았는지 확인한다.
7. Pull Request에 변경 이유, 사용자 영향, 검증 결과, 남은 위험을 적는다.
8. 검토가 끝나면 개별 커밋이 남도록 rebase merge한다.

## 커밋 크기 판단법

다음 질문에 모두 `예`라고 답할 수 있으면 적절한 크기다.

- 이 커밋을 한 문장으로 설명할 수 있는가?
- 이 커밋만 되돌려도 다른 기능이 망가지지 않는가?
- 변경 이유가 하나인가?
- 필요한 테스트가 같은 커밋 안에 있는가?
- 커밋이 끝난 상태에서 빌드하거나 테스트할 수 있는가?

다음 변경은 서로 다른 커밋으로 나눈다.

- 문서 규칙 추가와 실제 기능 구현
- 리팩터링과 사용자 동작 변경
- 전사 API 계약 변경과 관계없는 화면 스타일 수정
- 버그 수정과 전체 파일 포맷 정리

프론트엔드 타입, 백엔드 스키마, API 구현이 하나의 계약을 완성한다면 함께
커밋한다. 중간 커밋에서 계약이 깨지는 것보다 하나의 완전한 원자적 커밋이 낫다.

## 커밋 메시지 형식

```text
[종류] 무엇을 왜 바꿨는지 알 수 있는 한글 제목

- 변경 사항 1
- 변경 사항 2
- 추가하거나 수정한 테스트

검증:
- 실행한 명령
- 실행하지 못한 검증과 이유
```

좋은 예:

```text
[fix] 빈 전사 결과가 평가 단계로 넘어가지 않도록 차단

- 공백만 포함된 STT 응답을 전사 실패로 처리
- 사용자에게 다시 녹음할 수 있는 오류 메시지를 반환
- provider와 API 오류 응답 테스트 추가

검증:
- python -m pytest tests/test_transcriptions.py
- python -m ruff check app tests
```

나쁜 예:

```text
[fix] 오류 해결
```

무엇이 잘못되었고 어떤 동작이 달라졌는지 알 수 없기 때문이다.

## Pull Request 체크리스트

- [ ] 제목과 설명이 한글로 구체적으로 작성되어 있다.
- [ ] 변경 목적이 하나로 묶여 있다.
- [ ] 사용자에게 보이는 동작 변화를 설명했다.
- [ ] 테스트, lint, build 결과를 기록했다.
- [ ] 실행하지 못한 검증과 이유를 기록했다.
- [ ] API 키, 음성, 전사문 같은 민감 정보가 로그나 fixture에 없다.
- [ ] API 계약이 바뀌었다면 프론트엔드, 백엔드, 테스트, 문서를 함께 확인했다.
- [ ] 모델이나 프롬프트가 바뀌었다면 STT 평가 결과를 비교했다.
- [ ] 남아 있는 제한과 후속 작업을 적었다.

## 병합 원칙

- `main`과 `develop`에는 Pull Request를 통해서만 병합한다.
- 원자적 커밋을 보존하기 위해 기본 병합 방식은 rebase merge로 한다.
- 검증에 실패한 커밋은 병합하지 않는다.
- 이미 공유된 브랜치의 기록을 강제로 덮어쓰지 않는다.
- 긴급 수정도 테스트와 상세 커밋 본문 규칙을 생략하지 않는다.
